# Playbooks（Grok Bot 版）

来源：pstack v0.15.36 `skills/poteto-mode/playbooks/` 共 23 套。本版合并为 8 套，步骤按原文压缩，删掉 Cursor 专属机制（Task 子代理、`/loop` 唤醒、watch-pr 脚本、Origin/gt 工具链）。被合并或删掉的清单见 `../README.md` 的“砍掉了什么”一节。

每套 playbook 开始前，先按 `00-poteto-mode.md` 写 throughput checkpoint。

## Investigation（只读调查）

只出带引用的解释或建议，不改代码。

1. 走 `10-how-why.md` 的 how。问动机时再走 why。
2. 检查点只写一行：`throughput checkpoint: n/a, read-only investigation`。
3. 输出 how 的形状：Overview、Key Concepts、How It Works、Where Things Live、Gotchas。做决策比较时给 tradeoffs 表。
4. 回复要干净短句。结论写清自己的真实判断和理由，前提错了就直说。

没有 PR，没有 babysit，没有 architect。除非调查本身就是为了之后改代码，那时把结论交给用户，再按 Bug fix 或 Feature 重走。

## Bug fix（修 bug）

你拥有这项任务。计划、评审、验证都在你手里。实现可以分给新会话。

讲科学。每一行发出去的代码都要有运行时证据。可能有帮助的兜底不是修法，是假设。不发。证据推翻了假设，就 revert 它引起的东西。证据支持的最小改动才发，别的都不发。

1. **自己先复现**。在同一表面上跑出来。复现不出来就合成触发条件、收紧条件或加插桩，直到它触发。只在控制面确实够不到目标、且已经推到极限时，才问用户，并写清具体原因。
2. **二分找原因**。列候选假设，逐个排除。用 how 摸清相关子系统，用 why 查回归历史。每次取切分面最大的那一半，拿运行时证据，淘汰。状态不清楚就加日志或插桩，边跑边读。不要猜。确认存活下来的**机制**有运行时证据，再进第 3 步。
3. **定修法**。跨函数边界先过 `08-architect.md`。实现分给新开的 Grok Bot 会话，带上明确范围。
4. **在同一表面验证**。原始复现现在必须通过。“不确定”或“表面不对”不算通过。单元测试只能证明分支行为，不能证明 bug 不存在。
5. **提交顺序**。先提交能复现失败的测试或复现，再提交修法（failing test first，修法在上）。测试成本太高或集成太重时跳过这条。
6. 走 `05-review.md` 开 PR。

**回复**：坏了什么、根因、修法、怎么验证的。失败再通过的复现输出原文贴出。

## Feature（新功能）

你拥有设计。计划、评审、验证都在你手里。实现分出去，你留在主导位。

1. 对相关子系统跑 how。
2. 过 `08-architect.md` 做并行设计探索。
3. 写 throughput checkpoint（四项，见 `00-poteto-mode.md`）。
4. 实现分给新开的 Grok Bot 会话，带上明确范围（文件路径、命名的数据形状及组织方式、成功标准）。实现有多种合法形状时（错误处理、抽象层、测试结构），用 `07-interrogate.md` 的对抗方式先让不同会话各出一版，再合成。不要跳过这步。评审分离本身就是收益，不省。
5. 在匹配的表面上验证。“不确定”或“表面不对”不算通过。
6. 重排成小而有序的 commit。一个单元建好、验好、提交，再做下一个。后续跟进叠上去。
7. 设计有争议先过 `07-interrogate.md` 再发。
8. 走 `05-review.md` 开 PR。

一个功能或一次迁移交给一个 owner，检查点 inline。owner 在阻塞阶段后内部再分。父级分流只用于产出独立产物的切片（审计、跨子系统调查、竞争实验）。

**回复**：建了什么、选了什么和为什么、检查点、还 open 的决定。设计备选给表。

## Refactoring（重构，行为不变）

1. 行为不变是硬标准。先给改动范围写出可观测的行为清单（测试、真实调用、输出）。
2. 小步走。每步改完跑清单，绿了再下一步。
3. 顺手删死代码与重复（laziness protocol，subtract before you add）。
4. 不修顺手看到的 bug。看到就记下来，另开 PR。
5. 走 `05-review.md` 开 PR，PR 正文写清行为为什么没变、用什么证明的。

## Prototype（原型，替决策省钱）

一个问题能通过观察解决时，不要问人。做一个用完就扔的草图。

1. 只回答一个问题。写清它。
2. 用最糙的实现让现象出现。不要打磨。
3. 记录观察结果（截图、输出、计时）。结果就是决定。
4. 草图不进主分支。决定了就按 Feature 或 Bug fix 重走。

## Perf issue（性能问题）

1. 先有基线数字。没有基线不谈优化（explain the number：先说清数字受什么限制，排除它测的是别的东西）。
2. 追踪到热点，再动手。不要凭感觉改。
3. 一次只改一个变量，前后对照，数字说话。
4. 持续爬坡同一个指标时，每轮一个假设、一次前后测量、一个 commit 只收赢的那次。这就是 hillclimb。输了的改动 revert，不留着。

## Multi-phase plan（多阶段 / 多 PR 计划）

计划本身就是交付物。不要边计划边实现。

1. 一两个文件、思路明显时跳过计划，直接说并停下。
2. 先用 Prototype 解决 open 问题。每个原型留分支、SHA 与截图。
3. 把骨架抄进计划文件（放仓库 `docs/` 下），填满每个占位。标题与子块顺序不要改。一个 PR 一节，一个 PR 只做一个带证据的改动。写清执行用的 playbook（可合入用 `05-review.md` 的 Shipping 思路，不合入用 Babysit 思路）。
4. 每个 PR 的验证块第一句永远是：测试 alone 不够。 PR 只有在单元、真实表面、性能三块都打勾时才算验过。真实表面那块强制要有。
5. 人只在明确说“开始执行”后才执行。执行前把计划路径贴给人，等批复。

## Autonomous run / 过夜跑

见 `09-loop.md`。核心：先把完成条件写成可检查的谓词，再开始。每次迭代只做证据支持的最小改动，验过就提交，没进展就丢弃。每次迭代在 `decisions.tsv` 记一行。永远不要悄悄放宽完成条件来宣告胜利。

## Babysit / Shipping（跟进与合入）

见 `05-review.md`。核心：先把整个栈建完、变绿，再跟进。合入只合从底部连续验证过的那一段，一次一个，自底向上。
