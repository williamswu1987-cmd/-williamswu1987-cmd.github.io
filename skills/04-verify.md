# 验证技能（Grok Bot 版）

来源：pstack v0.15.36 `skills/create-verification-skill/SKILL.md` 与 `skills/maintain-verification-skill/SKILL.md`。
原版把生成的 skill 写进 `.cursor/skills/verify-<app>/`。本版写进仓库的 `skills/verify-<app>.md`，Grok Bot 直接读。

每个正经项目都需要一个脚本化的办法，像用户一样驱动真实应用并证明行为：启动它，按用户的方式跑一个功能，留下证据。

## 1. 先问仓库，不要问人

从代码里回答下面这些问题，只问用户代码里看不出来的：

- **表面**：用户实际碰到的是什么？网页 UI、CLI、桌面应用、API、移动应用、库？一个仓库可以有多个，挑主要的，其余记下来。
- **启动**：本地怎么启动？优先用仓库自己的文档命令（package scripts、Makefile、README quickstart）。记端口、环境变量、种子数据、认证。
- **驱动**：agent 怎么用程序驱动它？先找现成工具：Playwright / Cypress 用例、expect 脚本、PTY 辅助、能 curl 的接口、调试端口。没有再选通用办法：网页与 Electron 用浏览器，CLI 用 tmux / PTY，服务用纯 HTTP。
- **观察**：能留下什么证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离**：两个实例能并排跑吗（端口、数据目录、profile）？不能就在生成的 skill 里写明：拒绝双开共享实例，宁可不验，也不要污染用户的会话。

仓库当前状态如果编译不过或启动不了，先修好（或精确汇报），再生成 skill。在坏底子上写的 skill 会教错步骤。

## 2. 生成 skill

写 `skills/verify-<app>.md`，每节都按实际摸到的情况写，不要留占位符：

- **Launch**：启动应用做验证的准确命令，以及怎么判断它就绪了（某行日志、某个提示）。就绪指可用，不只指进程有响应。数据库健康检查通过时初始化脚本可能还在跑。含 teardown。短命 CLI 没有常驻服务：启动指先构建一次二进制（或装依赖），再给每次驱动开独立的 PTY 或 tmux 会话。
- **Doctor**：一个只读检查，回答“这个实例值得驱动吗”：进程在、版本对、端口是我们占的、认证有效。任何地方看起来不对，先跑这个。
- **Drive**：驱动办法，用仓库里真实的 selector 与命令，不要举例子。优先稳定的把手（ARIA label、data 属性、提示字符串、路由路径），不要用坐标与 tab 顺序。
- **Evidence**：证明要抓什么、放哪里。证明标准：走真实用户路径，不要用内部 setter 或测试专用接口；同时抓动作与结果状态，不只抓最后一屏；可见变化之外，副作用也要验（写了文件、插了行、发了消息）；mock 只用在生产边界本来就隔离了外部系统的地方。安全路径是 dry-run 或测试模式时，靠观察（文件、网络、git 引用）验证它到底跳了什么，不要信名字。有些 dry-run 还会碰网络或开浏览器。
- **Cleanup**：怎么拆掉本次运行创建的实例。不要按进程名杀，杀自己启动的。清理删实例与临时状态，不删证据。证据在 skill 点名的位置活下来。
- **Helpers**：skill 带的脚本必须可执行，调用方式写在 skill 正文里。读的人要反推才能用的不算 helper。

## 3. 播 Feature Map

在 `skills/verify-<app>-features.md` 里建索引，再给每个能识别的用户功能写一节（先做最重要的 3 到 5 个，从路由、命令、菜单或文档里找）。每节回答四个问题：这功能是什么、用户怎么走到它、怎么用驱动工具跑它、什么可观察的终态能证明它工作了。再加一节 Gotchas。如果种子数据缺某个旅程的前提条件，旅程就报失败，原因写进该功能的 Gotchas。永远不要为了通过而放宽旅程。map 是仓库维护的验证源。只跑一个方便的入口不算验完，map 上列了别的入口就都要覆盖。

## 4. 生成完自己先跑一遍

按生成的 skill 从头跑一次：启动、doctor、驱动**一个** map 上的功能（一个就够，map 是为了以后的覆盖）、抓证据、清理。清理后确认证据还在点名的位置。清理吃掉证据等于这步失败。修好再跑，失败的每次迭代后也要跑清理，别让坏掉的尝试把进程和端口留在那。没执行过的 skill 是草稿，不是交付物。如果是在替代品上验证的（容器替新虚拟机、本地栈替远程），列出替代品替目标做的每一步。这些步骤在目标上跑过之前，都算未验证。

## 5. 维护

应用变了，map 也要跟上。每次改功能区时顺手更新 `skills/verify-<app>-features.md`。map 里写的东西与现实不符时，优先怀疑 map，再怀疑代码。
