# 过夜跑与决策记录（Grok Bot 版）

来源：pstack v0.15.36 `skills/poteto-mode/playbooks/autonomous-run.md`、`skills/show-me-your-work/SKILL.md`、`skills/ketchup/SKILL.md`、`docs/guide/07-overnight.md`。
原版用 Cursor 的 `/loop` 内置唤醒机制与跨模型家族评审。本版：循环就是一次次调用 Grok Bot；凌晨评审由全新 Grok Bot 会话做，替代跨模型评审。规则本身不变。

## 先赚信任，再谈过夜

没赚到信任的循环只是更快地生产未经检查的工作，错误一轮轮放大。放手跑之前，四条都要成立：

- 这件任务你手工做过一次，或看 agent 做过，知道什么是好的结果。
- agent 有你自己会用的工具与信号：验证技能、profiler、日志。
- 每个阶段都能证明自己的工作，达不到标准能停线。
- 你读过几份记录，把重复失败变成了工具、技能或检查。

四条不全时，在旁边看着跑。不要放手。

## 过夜合同

一份好的交接有目标、完成条件、权限与逃生口。不用长。模板：

```text
去睡了。把所有调用方迁到新解析器，在 <base> 之外的新工作区做。
完成条件：零旧调用方、全部解析器 fixture 通过、旧 API 已删。
记 decision log。提交前不要问我。
如果几个小时后真的卡死了，停下来写清原因。
```

每句话买的东西：

- “去睡了”是自主授权。agent 停止发问，继续跑。
- “完成条件是……”把目标变成每次迭代都能跑的检查。
- “新工作区”让运行不撞上你手头开着的东西。
- “提交前不要问我”预先回答了 agent 否则会卡住的权限问题。
- 逃生口让它在真正死胡同时停下写原因，胜过八小时创造性地重新解释目标。

**坑**：时长不是完成条件。“干四个小时”给 agent 的不是能通过或失败的谓词，醒来只会看到四小时的动作，不是结果。

## 循环怎么做

一次迭代只做一件事：

1. 检查完成条件。
2. 做证据支持的最小改动。
3. 对着真实产物验证。
4. 有进展就提交，没进展就丢弃。
5. 在 `decisions.tsv` 记一行。

改动没用就丢掉，不要留着 ride。平台期意味着换打法，不是停下。永远不要悄悄放宽完成条件来宣告胜利。

一次迭代的发现如果支持目标，顺手处理：坏掉的 skill、相关 bug、不稳定的验证器、评审噪音、工具故障、孤儿后续、可修的漂移。放进自己的 PR。不要把可逆工作推给人，也不要发问。只报不可逆动作、实验无法解决的真正产品或偏好问题、或真实死胡同。每次支线修好回到主谓词。

## decisions.tsv

一份 canonical log。一个文件，一行一个决策。单元格永远单行。证据是指针，不是散文。

列（见同目录 `decisions-template.tsv` 的表头与例子）：

| 列 | 写什么 |
|---|---|
| ts | ISO8601 时间戳 |
| phase | 阶段或工作流 |
| decision | 选了什么或做了什么，一行 |
| why | 理由，说人话。某条原则驱动了就直说，不要贴术语标签 |
| evidence | 能证明它的链接或路径：commit SHA、PR 号、`文件:行号`、产物、trace、截图路径。永远不要写一段话 |
| result | 结果或谓词状态：`tests green`、`reverted`、`pixel-diff 0`、`INCONCLUSIVE`、`open` |

`scripts/log.sh` 不存在于本版。用 `printf` 追加一行即可，单元格里有制表符或换行先清掉，以 `=`、`+`、`-`、`@` 开头的单元格前面加一个单引号。

记决策点与检查点，不记每个动作：选了 fork、一个单元完成及其验证结果、触发了 pivot 或 revert、浮现了 blocker、修好了 gate。循环运行时每次迭代一行。跳过琐碎与自证的。

一次运行就是一次 agent 对话，含它后来的回合与对它的总结。接手、换 agent 或新开聊天都是新运行。新运行在已有 log 上追加时，第一行 phase 写 `start`，并点名它没写的前面那些行的 `ts` 范围，evidence 写这次运行的标识（如 agent id）。`start` 只做这个用。

放哪里：默认不提交。工作目录下的 `decisions.tsv`，多个任务并行时用 `.audit/<任务名>.tsv`，不要进 git。只有工作量大到评审需要这条轨迹来信任结果时才提交。

规则：

- 只追加。一个错误的决定用新行取代。永远不要改历史、删历史。
- 优先用已提交的脚本产出证据，不要用手工一次性产物。
- 交回前先审计 log 是否说了真话。对照实际发生的事走一遍本轮的行。每个决策与动作都要有真实映射，证据都要能解析并证明所称之事。 shaped 工作但没记下来的 fork、pivot 或放弃的方案是缺口，补上。审计永远不改、不删已有的行。错的行用新行取代并写清实际发生了什么。

## 早上审计

回来先看 log，再让 agent 出 catch-up：

```text
跟我说说昨晚做了什么
```

交回之前，agent 要新开一个 Grok Bot 会话读 trail 与记录，标出值得注意的事。回复最后加一节 Attention，先写一行评审会话的标识，再逐条列出 flag，指向具体行或时刻。“没有 flag”是合法值。每条 flag 类别：

- 证据薄弱或没有证据的决策。
- 跳过或声称了但没有证明的验证步骤。
- 事后看有风险的选择（操之过急、范围蔓延、给症状贴了补丁）。
- 粗看会漏的缺口。

先读 Attention，再读它指向的 log 行。你在审计决策，不是从头读一整夜。

## 快速近况（ketchup）

只要近况不要审计时，用这个。只读，不改代码、不启动应用、不发东西。收集上次对话以来本会话的工作、新会话的汇报、以及别人发来的消息。先核对每个 PR、CI 或 agent 的当前状态，再写。每个数字都要对得上事实来源。

回复控制在 100 词以内说清发生了什么（图片不计）。然后每件等人决策的事给一句话所属的事：叫什么、改了什么、证据、风险、你的倾向。没有等人的事就直说没有，停下。

## 队列与长期项目

一晚上是一队独立改动或一整个项目时，同一套信任往上扩：每个 PR 一个 owner 从建到合入全程负责；每个 PR 的合入 verdict 必须来自没写它的人；一次先跑通一个单元再铺开。见 `05-review.md` 的 Shipping 与 `02-playbooks.md` 的 Multi-phase plan。
