# 对抗审查（Grok Bot 版）

来源：pstack v0.15.36 `skills/interrogate/SKILL.md` 与 `skills/arena/SKILL.md`。
原版用多模型并行出对抗方与交叉裁判。本版单模型：对抗方是依次开的新 Grok Bot 会话，每人独立工作区；裁判由主会话自己担任，按同一份打分表逐项读。并行变串行是唯一的结构变化，规则本身不变。

## 立场

对抗方想办法打烂一个改动或一个设计。只有被真实运行证明的发现才活下来。汇报发现。不直接修。

## 定范围

范围是用户点名的。否则就是分支 diff，从与 base 分支的 merge base 起，含工作区。先用自己的话复述意图（来自用户消息、commit 与 PR 描述）。意图不清楚先问用户。

## 派出对抗方

开 2 到 3 个全新的 Grok Bot 会话。每人给同一份简报：范围、意图、以及下面这段原文：

> 打烂这个改动。用针对真实代码的运行证明每个发现，比如失败的测试、复现脚本，或打印出错误行为的命令输出。设计或方案类的，跑原型或探查当前树。复现放在自己的工作区。每个发现汇报标题、确切命令、它打印的输出，以及意图要求的输出。没跑过的不要写，包括风格、命名、结构，以及需要未来改动才有意义的风险。零发现是合法结果。

每人一份独立输出位置（能用 git worktree 最好，否则各用自己的目录）。不要让对抗方互相看到对方的发现。

## 验证

主会话逐条重跑每个发现给出的命令。输出确实显示失败、且失败破坏意图时，保留。其他的丢掉。同一个根因的发现合并。

## 输出

- **意图**：复述。
- **发现**：每个被验证的发现给命令、输出、它怎么破坏意图、是哪个对抗方找到的。没有活下来的发现时写“零已验证发现”。
- **丢掉的**：每个对抗方丢了几条、为什么丢。

## 什么时候用

设计有争议、改动跨边界、合入前心里没底时用。不是每个 PR 都要跑。对抗审查的成本是两到三轮完整运行，只在值得的地方花。
