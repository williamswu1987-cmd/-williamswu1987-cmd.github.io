# 先搞懂再动手（Grok Bot 版）

来源：pstack v0.15.36 `skills/how/SKILL.md`、`skills/why/SKILL.md`、`skills/teach/SKILL.md`、`skills/recall/SKILL.md`。
原版用 Cursor 的 Task 子代理分 explorer / explainer / investigator 多路并行。本版单模型：改成主会话内分步做，复杂时开新 Grok Bot 会话做独立角度，回来再由主会话合成。规则与输出形状不变。

## how：这东西怎么工作

回答“X 是怎么工作的”。产出 senior 工程师接手一个子系统时需要的架构解释：能建立可用的心智模型，不过度到像带注释的源码。

- **简单**（一个模块、一个小工具、窄问题如“函数 X 怎么工作”）：直接探索并解释，一次完成。
- **复杂**（跨多个文件或服务、跨领域、全架构概览）：先拆成 2 到 4 个角度，每个角度开一个全新 Grok Bot 会话独立探索，回来由主会话合成。

输出章节（不适用的删掉）：Overview、Key Concepts、How It Works、Where Things Live、Gotchas。

## why：为什么长这样

回答是什么力量让代码长成这个形状。how 回答代码做什么、怎么做。why 回答动机。

步骤：

1. **定目标与问题**。目标通常是一块代码、一个模式、一个命名决策。问题通常是设计 rationale、tradeoff、边界 case、外部约束、死代码或历史全景。目标模糊时按上下文猜一个并写清，方便人纠正。
2. **建代码锚点**。动手前先在正文里写好种子上下文：文件路径与行范围、关键符号、最后几次碰目标的 commit、merge commit 里的 PR 号、关联 ticket。用 `git blame`、`git log --follow -p`、`git log --oneline -20` 挖。实质性 commit 去拉 PR 正文与讨论。
3. **并行调查**。按证据类别分角度（源码历史、issue tracker、长文档、实时聊天记录、基建可观测性、报错追踪、产品分析），每个角度独立探索。不要混在一起。
4. **合成**。写成带引用的判断：决定是什么、tradeoff 是什么、信心有多高。知道的与推断的要分开写。

## teach：讲清楚

有人（或未来的 agent）要接手时用。逐点解释机制，甚至自证“为什么不用另一种方案”。解释要带上如果换方案会失去什么。

## recall：找回上下文

前几天聊过的上下文丢了时用。按关键词与时间翻历史对话与记录，把相关结论贴回来，不要凭记忆复述。

## 原则

- 搞懂先于动手。非平凡改动、架构决定、“确定吗”这类问题先过 how。
- 命名文件不算摸清。产出能讲清运行时流向与归属的解释才算。
- 证据类别之间不互相替代。git 历史说不了线上报错，聊天记录说不了代码现状。
