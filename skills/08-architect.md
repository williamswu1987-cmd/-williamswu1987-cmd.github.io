# 架构草图（Grok Bot 版）

来源：pstack v0.15.36 `skills/architect/SKILL.md` 与 `skills/arena/SKILL.md`。
原版用 arena 多模型并行出候选方案再交叉裁判。本版单模型：候选方案由主会话依次写出（每版独立，不互相抄），裁判由主会话按打分表自己做。需要第二意见时，新开一个 Grok Bot 会话做独立评审。

## 流程

开一个 todo list，每阶段一项，再开工：

1. Ground（摸清）
2. Sketch（画草图）
3. Agree（定稿）
4. Implement（实现）
5. Scrap（推倒）

## Phase A：Ground

对新代码要碰的每个系统建立真实心智模型。跑 `10-how-why.md` 的 how。只点文件名不算摸清。要产出 how 要求的那份架构解释。如果设计重新定义归属或分层，再对现有形状跑 why，让 rationale 变成约束，不是猜测。

真正绿地、没有任何周围系统要集成时，才能跳过这步。

## Phase B：Sketch

要求至少两个结构上不同的候选方案，哪怕第一个看起来已经够了。这是 exhaust the design space 原则的落地。整体形状的备选，不是同一个形状里的点修。

每个候选方案先过一遍红旗检查。再合成之前，逐条自查：

- 下一个贡献者只打开自己要改的文件、抄最近的例子、走最短能编译的路。哪个设计下这样做还是对的？
- 比较候选方案的接口深度。优先把更多复杂度藏在更小更简单的公开表面之后。
- 调用方的写法先定。先写调用方怎么用，再推类型与签名。

合成时选一个底座，再把落选方案里值得的东西嫁接进去（通常每家一到两处，不要大半搬过来）。嫁接要手工揉进同一个心智模型，不要机械粘贴。候选方案收敛到同一个形状是强一致信号，直接发共识形状，不用嫁接。候选方案 wildly 发散说明 Phase A 没定够，重新框定再跑一遍，不要平均它们的分歧。

输出：一份类型与签名草图（`not implemented` 的空体加伪代码），小改动一个文件，大改动加模块地图；一份 rationale，含用法草图与合成决策。

## Phase C：Agree（可选）

默认直接按合成设计实现，不设人工检查点。只有调用方明确要求（“先给我看看再实现”之类）时才停下来等批复。

合成设计本身可以先作为一个 commit 发出去（脚手架先行）。填充期间计划内、定好范围的破损没问题。

实现前想上对抗压力时，对合成草图跑 `07-interrogate.md`。

人对形状有异议时（检查点上或事后），把它当 Phase A 的证据。重新摸清，重新跑 Phase B，再写更多代码。

## Phase D：Implement

把 `not implemented` 的空体换成代码，伪代码换成逻辑。合成草图就是合同。偏离草图是信号，要报出来，不是顺手吸收的摩擦。某个函数需要草图没想到的参数时，先问：草图错了、需求漏了，还是实现越界了。

## Phase E：Scrap（架构错了就推倒）

实现持续产生草图兜不住的摩擦时，把草图扔掉。不要在错误的设计上打补丁。信号看模式，不是单点：

- 同一形状的绕过办法在无关代码里反复出现。
- 多个无关 edge case 全要特判分支。
- 类型需要逃生口（`any`、强转、实践中永远有值的可选字段）才能编译。
- 草图说状态不共享，实现却到处想加锁。
- 调用方必须懂抽象的内部规则才能用。
- 实现中出现两次以上同一形状的 Phase D 偏离。

推倒时：

1. 对已建的东西重跑 how。
2. 按 redesign from first principles，把新约束当成第一天的假设重新设计。
3. 按 subtract before you add，新草图先比旧的更小，再长大。
4. 回 Phase B 重跑。
